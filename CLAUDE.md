# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это за репозиторий

Это не программный проект, а учебный курс по DevOps на русском языке — набор Markdown-файлов, публикуемых как сайт GitHub Pages (`_config.yml`, тема `jekyll-theme-cayman`). Кода, сборки, линтеров и тестов нет: единственный «артефакт» — сами `.md`-файлы. Правка любого файла = правка опубликованной страницы курса.

## Структура и навигация

- `README.md` — главная страница: как проходить курс, описание сквозного проекта, таблица тем с оценкой времени, ссылки на ТЗ. Это единственный индекс — **любой новый файл темы или задания обязан появиться в соответствующей таблице/списке README**, иначе он недостижим на сайте.
- `<N>-<Название>.md` — темы курса 1–9. Номер в имени файла = номер в заголовке `## N. ...` = позиция в README.
- `задание-мониторинг.md`, `задание-sre.md` — большие практические ТЗ, выполняются после всех тем.
- `Старые-уроки-и-задания.md` — имя историческое, внутри теперь «Дополнительные материалы и ссылки»: дорожная карта, внешние курсы, подборки. Файл не переименовывали, чтобы не ломать внешние ссылки. Вопросы с собеседований из него разнесены по темам.
- Имена файлов кириллические с дефисами; ссылки ведут на них напрямую, без URL-энкодинга. При переименовании файла нужно синхронно править README и соседние темы (см. коммит `759f386`).

## Обязательная структура файла темы

Каждая тема идёт строго в этом порядке:

1. `### [Вернуться к главной странице, списку всех тем](README.md)`
2. `## N. <Развёрнутое описание темы>` — тот же текст, что в README. Это объяснение «зачем тема нужна» человеческим языком, а не название инструмента («Упаковка приложений со всем необходимым для их работы…» вместо «Docker»).
3. **Блок-шапка пути обучения** в виде цитаты (`>`): «Что ты узнаешь», «Что нужно знать заранее», «Сколько времени займёт», «Твой шаг в сквозном проекте». Затем `---`.
4. Теоретические разделы `###` (внутри при необходимости `####`).
5. `### Теоретические вопросы` — нумерованный список, вопрос выделен `**жирным**`, следом строка `**Ответ:** ...`. **Вопрос без ответа — дефект**: в темах 4 и 5 они были и их пришлось дописывать.
5а. `### Вопросы с собеседований` — необязательный блок в том же формате, сразу после теоретических вопросов. Сюда попали вопросы из бывшего архива; они дополняют основной список, а не дублируют его.
6. `### Практическая часть` — задания `#### Задание N. <что сделать>` с подпунктами `**Цель:**`, `**Шаги:**`, `**Ожидаемый вывод:**`, `**Типичные ошибки:**`.
7. `### Проверь себя: тема освоена, если ты можешь` — чек-лист навыков (`- [ ]`), а не список прочитанного.
8. Ссылка на следующую тему в конце файла: `### [Следующая тема: … →]` с путём к следующему `.md`.

## Сквозной проект

Через все девять тем проходит одно приложение — веб-сервис «Заметки» (`notes`, `app.py` на голом `http.server` из стандартной библиотеки Python; эндпоинты `/`, `/healthz`, с темы 8 — `/metrics`). В каждой теме есть задание «Сквозной проект: …», добавляющее к нему очередной слой: systemd → nginx+TLS → git+CI → Docker+Compose → Kubernetes+Helm → облако → Terraform+Ansible → мониторинг → Vault+Flux.

При правке любой темы проверяй, что цепочка не рвётся: приложение, порты (8080), имена файлов (`compose.yml`, `deploy/`, `k8s/`, `chart/`, `infra/`) и незакрытые «долги» должны совпадать между темами. Пример намеренно оставленного долга: пароль базы открытым текстом в `compose.yml` темы 4 с пометкой «чиним в теме 9», где он и убирается.

## Дидактические приёмы, которых нужно придерживаться

- **Задания «сломай и почини».** Почти в каждой теме есть шаг, где ученик намеренно ломает работающую систему (останавливает приложение → 502 в nginx, ставит лимит памяти 8Mi → `OOMKilled`, ломает readiness-пробу → пустые endpoints, катит битую версию → откат Flagger). Это не украшение, а основной способ обучения диагностике — не выкидывай их при рефакторинге.
- **Обратные ссылки на пройденное.** Новая тема явно опирается на предыдущие: коды 502/504 из темы 2 всплывают в темах 4 и 5, `SIGTERM` из темы 1 — в Docker и Kubernetes, DNS по имени сервиса — в Compose и затем в кластере.
- **Разбор ошибок.** В `**Типичные ошибки:**` пишут реальную формулировку ошибки (`ImagePullBackOff`, `bad interpreter`, `port is already allocated`) и причину, а не общие советы.

## Jekyll и двойные фигурные скобки — обязательно к соблюдению

Сайт собирает GitHub Pages (Jekyll 3.10), и Liquid обрабатывает **все** `.md`-файлы до Markdown. Поэтому любые `{{ ... }}` и `{% ... %}` в тексте Jekyll принимает за свои теги. Последствия бывают двух видов, и второй хуже:

- сборка падает с `Liquid syntax error` — так уронила Pages конструкция `f'...{{status="{status}"}}...'` в примере на Python;
- **сборка проходит, но содержимое молча подставляется пустым** — Helm-шаблоны (`{{ .Values.image.tag }}`), переменные Ansible/Jinja2 (`{{ ansible_hostname }}`), аннотации Prometheus (`{{ $labels.instance }}`) исчезали со страниц, хотя в репозитории выглядели правильно.

Правило: всё, что содержит `{{` или `{%`, оборачивается в `{% raw %}` / `{% endraw %}`.

- для блока кода — теги ставятся **снаружи** ограждения, с тем же отступом, что у ```` ``` ````;
- для inline-кода — теги ставятся вокруг обратных кавычек прямо в строке.

Исключение — сам этот файл: он приводит Liquid-теги как текст и потому уронил бы сборку. Поэтому `CLAUDE.md` добавлен в `exclude` в `_config.yml` и на сайт не попадает. Если добавляешь в `exclude` что-то ещё, помни: указание своего списка заменяет стандартный целиком, поэтому в нём перечислены и обычные служебные пути.

Перед коммитом проверяй настоящим парсером Liquid, а не глазами (и учитывай `exclude` — проверять надо ровно то, что рендерит Jekyll):

```bash
gem install --user-install --no-document liquid -v 4.0.4
ruby -e '$LOAD_PATH.unshift(File.expand_path("~/.gem/ruby/2.6.0/gems/liquid-4.0.4/lib"))
require "liquid"; require "yaml"
skip = YAML.load_file("_config.yml")["exclude"] || []
(Dir.glob("*.md") - skip).each { |f| begin; Liquid::Template.parse(File.read(f)); rescue => e; puts "#{f}: #{e.message}"; end }'
```

Проверка обязана быть двойной: файл не только разбирается без ошибок, но и после `render` сохраняет содержимое шаблонов.

**Запускай её последним действием перед коммитом.** Ровно на этом уже обожглись: проверку прогнали, потом дописали текст с тегами — и сборка снова упала.

## Стиль текста

- Русский язык, обращение к ученику на «ты», аудитория — новичок без опыта в IT. Термины поясняются при первом появлении, английский оригинал в скобках: `Observability` (наблюдаемость).
- Комментарии в коде и конфигах — на русском и объясняют, зачем строка нужна. Они часть учебного материала, не сокращай их при рефакторинге примеров.
- Версии инструментов указываются явно и закрепляются (`prom/prometheus:v3.1.0`, `nginx:1.27.3`, `postgres:17-alpine`), текст ссылается на актуальный год. При обновлении содержимого проверяй согласованность версий и датировок — этим занимались отдельные коммиты (`1767c40 Updated 2026`).
- Следи за устареванием команд: в старых редакциях находились `actions/checkout@v2`, `kubectl run --generator=run-pod/v1` (удалён в k8s 1.18), `version: '3.8'` в Compose. Проверяй примеры на актуальность, прежде чем оставлять их.

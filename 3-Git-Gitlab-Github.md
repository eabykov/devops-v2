## 3. Управление версиями проектов, автоматизация при внесении изменений

Представьте, что вы и ваши друзья вместе работаете над книгой. У вас есть множество версий текста, и вы постоянно вносите изменения: что-то добавляете, что-то удаляете. Чтобы не запутаться в этих изменениях, вы используете Git. Его цель — помочь вам следить за тем, кто и что изменил, и легко возвращаться к старым версиям, если что-то пошло не так. Это позволяет вам работать вместе без страха потерять важную информацию.

### Основные задачи Git

- **Отслеживание изменений:** Каждый раз, когда вы вносите изменения в проект, Git запоминает их, создавая так называемую «версию» или «коммит». Это позволяет вернуться к любой предыдущей версии кода, если вдруг понадобится откатиться назад.
   - **История изменений:** Git хранит всю историю изменений, включая комментарии о том, почему были внесены те или иные правки. Это помогает понять, что именно было сделано и кем.
- **Совместная работа:** Несколько разработчиков могут одновременно работать над одним проектом, вносить свои изменения и затем объединять их через Git, решая все расхождения. Например, если они редактировали один и тот же текстовый файл, они выбирают, чьи коммиты в итоге останутся. Это особенно полезно для больших команд, где важно координировать работу разных людей.
   - **Управление ветками:** Ветка (branch) — это отдельная линия разработки проекта. Например, одна команда может работать над новой функцией в отдельной ветке, а другая — исправлять баги в основной ветке программы. Когда всё готово, ветка, где разработчики работали над новой функцией, вливается в основную ветку.

### Основные понятия Git

1. **Репозиторий** — это каталог, в котором хранятся все файлы проекта и история их изменений. Git хранит эту историю и настройки в репозитории в специальной директории `.git`.
3. **Коммит** — это зафиксированные изменения с описанием того, что было сделано.
4. **Ветка** — это отдельная линия разработки, позволяющая работать над проектом независимо от основной линии.
5. **Слияние (merge)** — это процесс объединения изменений из одной ветви в другую.
6. **Конфликт** — это ситуация, когда два разработчика вносят изменения в один и тот же файл, и необходимо решить, чьи изменения оставить.
7. **Клонирование** — это создание локальной копии удаленного репозитория.
8. **[GitHub](https://github.com)** — это онлайн-платформа, которая предлагает удобный способ хранения репозиториев.
9. **Push/Pull** — это операции отправки и получения изменений с удаленного сервера репозитория, например [GitHub](https://github.com).
10. **Tag** — это метка, которая отмечает важные события в проекте, такие как выпуск версии. Tag аналогичен ветке, но в него нельзя вносить изменения.

### GitHub

GitHub — это онлайн-платформа для хранения кода и совместной работы над программными проектами с использованием Git. Представь себе огромный склад, где программисты могут хранить свои git-репозитории, делиться ими с другими людьми и вместе работать над ними.

> Например, это обучение размещено на GitHub в виде репозитория: [github.com/eabykov/devops](https://github.com/eabykov/devops)

### CI/CD автоматизация

Представьте, что вы строите дом на колёсах:
- CI - каждый член вашей команды выполняет свою часть работы: кто-то возводит стены, кто-то устанавливает окна, а кто-то занимается электропроводкой. В конце дня вы хотите увидеть, насколько хорошо все части дома сочетаются друг с другом.
- СI - Теперь представьте, что после завершения строительства вы проверяете, всё ли сделано правильно: работают ли окна, нет ли трещин в стенах и исправен ли свет. Это тестирование.
- CD - Когда проверка завершена, вы готовы отправить готовый дом его владельцам. Это процесс доставки или развёртывания.

CI/CD помогает сделать этот процесс для программ более быстрым и автоматическим, избавляя от необходимости ждать, пока кто-то вручную выполнит каждую задачу (например, команду в терминале или тестирование). Автоматизированная последовательность шагов называется пайплайн (pipeline).

На таких платформах, как GitHub и GitLab (по сути, это та же GitHub, только с возможностью установки на свой сервер и создания собственной онлайн-платформы, им пользуются большинство корпораций, т.к. хотят хранить свой код не в GitHub, а у себя на сервере), вы можете автоматизировать разные сценарии при разных событиях в Git-репозитории:
- коммит
- коммит в конкретную ветку
- слияние
- выпуск тега
- расписанию

В результате этих событий могут автоматически происходить различные шаги непрерывной интеграции и доставки (CI/CD), среди которых:
1. **CI Сборка проекта**: Когда вы отправляете изменения в репозиторий, проект автоматически собирается, чтобы убедиться в правильности работы после ваших нововведений. Сборка проекта — это процесс преобразования исходного кода, написанного программистом, в исполняемый файл, который компьютер может понять и запустить. Это можно сравнить с рецептом блюда на бумаге: чтобы приготовить само блюдо, необходимо следовать этому рецепту и использовать необходимые ингредиенты. Исходный код — это и есть тот самый рецепт, а готовая программа — уже приготовленное блюдо.
2. **CI Тестирование**: После успешной сборки проект может запускать тесты, чтобы проверить, нет ли ошибок в коде, запускается ли программа и работает ли она так, как ожидалось.
3. **CD Публикация**: Если все тесты пройдены успешно, ваша программа или сайт будут автоматически опубликованы (доставлены) с вашими изменениями, избавляя вас от необходимости делать это вручную.
4. **CD Интеграция с другими сервисами**: Вы можете настроить пайплайн таким образом, чтобы его шаги взаимодействовали с различными инструментами и платформами, такими как Telegram или облачные сервисы. Например об неуспешном шаге отправлялось сообщение в рабочий канал в Telegram.

# Вопросы и задания по теме "Управление версиями проектов и автоматизация"

## Теоретические вопросы (20 вопросов)

### Основы Git

1. **Объясните простыми словами, что такое Git и почему он нужен разработчикам?**
   - Ожидаемый ответ: система контроля версий, позволяет отслеживать изменения в коде, работать в команде, возвращаться к предыдущим версиям

2. **В чем разница между репозиторием и обычной папкой с файлами?**
   - Ожидаемый ответ: репозиторий содержит историю изменений в папке .git, отслеживает версии файлов

3. **Что происходит при создании коммита? Какую информацию он содержит?**
   - Ожидаемый ответ: фиксация изменений, содержит изменения файлов, сообщение, автора, время, уникальный идентификатор

4. **Объясните разницу между git add и git commit**
   - Ожидаемый ответ: add добавляет файлы в staging area (подготовка), commit фиксирует изменения в репозитории

5. **Зачем нужны ветки (branches) в Git? Приведите пример использования**
   - Ожидаемый ответ: для параллельной разработки функций, изоляции изменений, например main для стабильного кода, feature/login для новой функции входа

### Работа с ветками и слияние

6. **В чем разница между веткой (branch) и тегом (tag)?**
   - Ожидаемый ответ: ветка - активная линия разработки, можно добавлять коммиты; тег - неизменяемая метка версии

7. **Что такое конфликт слияния (merge conflict) и почему он возникает?**
   - Ожидаемый ответ: когда два разработчика изменили одну и ту же строку файла, Git не может автоматически объединить изменения

8. **Объясните разницу между merge и rebase**
   - Ожидаемый ответ: merge сохраняет историю веток, создает merge commit; rebase переписывает историю, делает ее линейной

9. **Что такое fast-forward merge?**
   - Ожидаемый ответ: когда ветка просто "догоняет" основную ветку без создания дополнительного merge commit

10. **Как можно откатить последние изменения в Git?**
    - Ожидаемый ответ: git reset для локальных изменений, git revert для уже опубликованных коммитов

### GitHub и удаленная работа

11. **Чем GitHub отличается от Git?**
    - Ожидаемый ответ: Git - инструмент контроля версий, GitHub - облачная платформа для хранения репозиториев и совместной работы

12. **Объясните разницу между git fetch и git pull**
    - Ожидаемый ответ: fetch загружает изменения но не применяет, pull = fetch + merge

13. **Что такое Pull Request (Merge Request) и зачем он нужен?**
    - Ожидаемый ответ: запрос на слияние изменений, позволяет проверить код перед добавлением в основную ветку

14. **Для чего используется файл .gitignore?**
    - Ожидаемый ответ: указать Git какие файлы не нужно отслеживать (логи, временные файлы, секреты)

15. **Как клонировать репозиторий и в чем разница с fork?**
    - Ожидаемый ответ: clone создает локальную копию; fork создает копию в вашем GitHub аккаунте

### CI/CD концепции

16. **Что означают аббревиатуры CI и CD? Объясните каждую**
    - Ожидаемый ответ: CI - Continuous Integration (непрерывная интеграция), CD - Continuous Delivery/Deployment (непрерывная доставка/развертывание)

17. **Что такое pipeline в контексте CI/CD?**
    - Ожидаемый ответ: последовательность автоматизированных шагов: сборка, тестирование, развертывание

18. **Какие события могут запустить CI/CD pipeline?**
    - Ожидаемый ответ: коммит, создание pull request, слияние веток, создание тега, по расписанию

19. **Что такое артефакты в CI/CD и зачем они нужны?**
    - Ожидаемый ответ: результаты сборки (исполняемые файлы, пакеты), используются для развертывания

20. **Приведите примеры того, что может включать "идеальный" CI/CD pipeline**
    - Ожидаемый ответ: сборка, линтинг кода, тесты, проверка безопасности, развертывание, уведомления

**Цель:** Научиться создавать репозиторий и делать коммиты

### Задание 2: Работа с ветками

**Задачи:**

### Задание 4: Решение конфликтов
**Цель:** Научиться разрешать merge conflicts

**Задачи:**
1. В репозитории создайте файл `config.txt` с содержимым:
   ```
   app_name=MyApp
   version=1.0
   author=YourName
   ```
2. Сделайте коммит
3. Создайте ветку `feature/update-version`
4. В этой ветке измените версию на 2.0
5. Переключитесь на main и измените версию на 1.5
6. Попробуйте слить ветку `feature/update-version` в main
7. Разрешите конфликт, выбрав версию 2.0
8. Завершите слияние

**Проверка:** Покажите итоговое содержимое файла и историю коммитов

### Задание 5: Простой CI/CD с GitHub Actions
**Цель:** Создать базовый автоматизированный workflow

**Задачи:**
1. В репозитории на GitHub создайте папку `.github/workflows/`
2. Создайте файл `simple-ci.yml` со следующим содержимым:
   ```yaml
   name: Simple CI
   
   on:
     push:
       branches: [ main ]
     pull_request:
       branches: [ main ]
   
   jobs:
     test:
       runs-on: ubuntu-latest
       steps:
       - uses: actions/checkout@v2
       - name: Check files
         run: |
           echo "Checking project files..."
           ls -la
           echo "Project validation complete!"
   ```
3. Сделайте коммит и отправьте изменения
4. Создайте новый файл `test.txt` и отправьте его
5. Посмотрите как сработал workflow в разделе Actions

**Проверка:** Покажите успешно выполненный workflow в интерфейсе GitHub Actions
